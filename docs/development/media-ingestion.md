# Private image ingestion development evidence

Updated 21 October 2026 for published source `c71f19d`. This records fictional-data development and isolated runtime evidence; it does not approve real child photos or a safeguarding operation.

The API has explicit fictional SQLite and actual PostgreSQL manifest adapters, a private local object store and an authenticated byte gateway. PostgreSQL uses current scoped RLS and purpose-bound non-owner API/worker roles. A future private bucket can replace the file adapter without changing audience checks; no paid bucket is provisioned.

The photo journey is prepare → authenticated bounded PUT → complete → exact-revision review or explicit manager Publish. A player completion creates a pending revision; a manager completion creates a private draft. Processing never publishes it. Replacement preserves the previous approved image until the new revision is approved. Logos have separate seasonless club/team ancestry, current kind-specific authority, rights/revision confirmation and versioned owning pointers. Team override removal restores the current club logo, then the neutral fallback.

## Current processing boundary

JPEG, PNG and canonical `image/heic` are supported up to 15 MiB and 40 megapixels, with a 60-second upload budget and short-lived write capability. Signature, size and SHA-256 are checked independently of the claimed MIME type. Original bytes must receive a clean configured scanner verdict before decoding. SVG/HTML/GIF and animated PNG are rejected. HEIC uses the pinned source-built helper in [infra/runtime/heic](../../infra/runtime/heic/NOTICE.md); unsupported/sequence or multiple-primary input and oversized hidden image items fail closed.

Decode/re-encode runs through short-lived bounded processes receiving generated private paths, never submitted URLs. The Node worker limits V8 heap, timeout, libvips concurrency and cache, and keeps its JPEG/PNG loader allowlist. HEIC is decoded separately into bounded raw pixels. This is process isolation and input bounding, not an independently reviewed OS sandbox or a guarantee over every native allocation.

Pinned `sharp@0.35.5` produces photo JPEG derivatives at longest edges 2048/480 and logo PNG derivatives at 1024/256, without upscaling. Logo alpha is preserved. Orientation is applied once and EXIF/GPS/ICC/XMP/comments are removed; no metadata-preserving API is used. The HEIC fixture proof verifies the resulting 32×64 orientation and metadata removal. Directories are 0700, object files 0600, and generated filenames contain no submitted filename or child label. Original/rejected-file retention and orphan cleanup still require Q09 and an operating owner.

Scanning is mandatory. Without configuration, completion returns `SCANNER_REQUIRED`; unavailable/error verdicts never become clean, and the original stays private for review/retry. The configured scanner uses fixed arguments/stdin, bounded time/output, no shell and no logged raw scan output. The [actual schema12 proof](evidence/2026-10-21/runtime/heic-schema12.json) used ClamAV1.5.4/database28157 for clean generated images and the harmless standard EICAR rejection probe. This establishes those observations, not an ongoing signature-update SLA or general antivirus efficacy. Real operation still needs maintained signatures, process/container hardening, moderation/retention ownership and approved publication policy.

Every photo derivative rechecks current team/season access, competition policy, hidden-uploader state and exact published/own/review revision. Logo derivatives recheck their current kind authority or published owning pointer. Gateways never serve originals and return `private, no-store`. Revocation, removal and replacement deny later requests; already viewed images or screenshots cannot be recalled.

## Client and observed evidence

The mobile/browser media clients call actual prepare/PUT/complete routes, retain the same identity/bytes for explicit retry, keep upload capabilities in memory and distinguish processing acknowledgement from publication. The fictional review can generate a PNG. Native library picking uses SDK-matched `expo-image-picker@58.0.10`, images only, with no camera/video/audio and no silent upload of a recovered Android picker result. Private derivatives are fetched through the authenticated gateway. Phone picker/cache/recovery behaviour remains unproved.

The source checkpoint passed 450 shared/platform tests and 219 API/access/worker tests with no skips. The [actual HEIC/scanner/restore proof](evidence/2026-10-21/runtime/heic-schema12.json) verifies original scanning, photo/logo derivatives, orientation once, metadata removal, rejected multi-primary/hidden-oversize input, scanner-unavailable refusal and exact paired database/object restoration. The [restricted schema12 runtime](evidence/2026-10-21/runtime/container-runtime-schema12-proof.json) passed migration/startup and 13 API/18 worker permission checks. [Logo browser evidence](evidence/2026-10-21/branding-ui-235f/evidence.json) and [public review evidence](evidence/2026-10-21/feature-completion/publication.json) establish their exact fictional upload/publication/inheritance journeys. These checks do not substitute for hardware or live operating acceptance.

Historical JPEG/PNG-only evidence recorded 15 media-service, five media-client and 25 community checks at that earlier checkpoint. Those counts remain historical; they are not the current suite or a statement that HEIC/scanning is unimplemented.

Not run on physical iPhone/Android: picker cancellation/limited access, file-URI handling, temporary-file/backup lifecycle, Android activity recovery, native image/cache behaviour and the complete phone upload journey against the configured identity/scanner/database. Real-data use remains subject to competition audience approval, privacy/retention, moderation/operator coverage and native security/device acceptance. No real child data is used in the retained fixtures.
