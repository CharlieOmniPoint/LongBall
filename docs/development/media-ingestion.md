# Private image ingestion development evidence

21 October 2026. This extends the fictional native/browser build; it does not authorise real child photos or claim a validated safeguarding operation.

The API now has a private local object-store adapter, persistent SQLite upload manifests and an authenticated byte gateway. `DevelopmentMediaService` in `apps/api/src/media.ts` receives the API database so linking a processed image and saving its community revision can share one transaction. A future private bucket can replace the file adapter without changing audience checks.

The upload journey is prepare → authenticated bounded PUT → complete → exact-revision review or explicit manager Publish. A player completion creates a pending revision. A manager completion creates an unpublished draft. Completion performs no publication. A replacement keeps the previous approved image until its new revision is approved. The worker receives only generated private local paths, never a submitted URL.

The technical development limits are JPEG/PNG, 15 MiB, 40 megapixels, a 60-second upload budget and a short-lived write capability. Byte signatures, size and SHA-256 are checked independently of the claimed MIME type. Animated PNG, SVG/HTML/GIF input and HEIC preparation are rejected; HEIC must pass a supported decoder test before being enabled. Decode/re-encode runs in a separate short-lived Node process, with a V8 heap bound, process timeout, single libvips concurrency, small cache and an explicit JPEG/PNG buffer-loader allowlist. This is process isolation and bounded input, not a claim of an independently reviewed OS sandbox or a bound on all native allocations.

Pinned `sharp@0.35.5` applies image orientation before creating JPEG display/thumbnail derivatives with longest edges 2048/480 and no upscaling. No metadata-preserving API is used. The derivative tests verify removal of EXIF/ICC/XMP/orientation metadata; no actual child data is in any fixture. Directories are 0700, object files are 0600, and generated filenames contain no submitted filename or child label. Originals and rejected files remain private; their production retention/erasure and orphan-cleanup policy still need Q09 and operating ownership.

Scanning is a separate mandatory boundary. With no configured scanner, completion returns `SCANNER_REQUIRED` and retains a private upload for retry. An unavailable/error verdict never becomes clean. `createClamAvScanner` invokes an operator-configured absolute executable with fixed arguments/stdin, bounded time/output, no shell and no logged raw scan output. `LONGBALL_CLAMSCAN_PATH` selects that executable. No ClamAV binary, signature database or update service was installed here; no live antivirus efficacy or freshness test is claimed. The tests inject a hash allowlist for known generated fixtures and test controlled process exit mapping separately. Real deployment needs maintained scanner databases, process/container hardening, abuse/retention operations and the approved photo policy.

Both full-image and thumbnail requests recheck current team/season access, publication policy, hidden-uploader state and the exact published/own/review revision through `authorizeCommunityMedia`. The gateway never serves originals and returns `private, no-store`. Revocation, removal and replacement block later requests. Already viewed images or screenshots cannot be recalled.

`MediaUpload.tsx` and the platform media client call the actual API prepare/PUT/complete sequence. They retain the same request identity and bytes for an explicit retry, keep the write capability in memory and distinguish processing acknowledgement from publication. The default review action uses a generated fictional PNG. Native library picking is a separate opt-in prop, with SDK-matched `expo-image-picker@58.0.10`; it uses images only, no camera/video/audio, and does not silently upload a recovered Android picker result. The client uses the connected credential adapter by default; public synthetic credentials require an explicit development prop. Current service refusal messages, including scanner-required, are shown without claiming success. Private derivatives are fetched through the authenticated gateway and held in memory while displayed.

Executed: 15 media-service tests covering the real sharp child decoder, orientation/metadata stripping, invalid/oversized/animated inputs, scanner refusal, owner/scope checks, stream integrity/limits, persistent/idempotent retries, exact revisions, replacement, removal, hidden uploaders and grant/policy changes. The adapter checks a ClamAV version response and the expected clean stdin result; an arbitrary successful executable is not accepted as a scanner. Five media-client tests cover actual binary request bodies, stable request keys, private header-only capabilities, error acknowledgement and authenticated gateway modes. Community rules separately have 25 tests including strict input parsing, public-command policy binding, ballots and media access. Scoped lint and mobile TypeScript checks pass. These are Linux/Node/browser checks, not phone results.

Not run on physical iPhone/Android: library picker cancellation and limited-photo access, native file-URI reading, temporary picker-file lifecycle/backup exclusions, Android activity destruction/recovery, native in-memory image/cache behaviour, signed permissions, a real scanner/database and a connected real-account upload. Real-data use remains gated by identity, competition publication policy, consent/privacy/retention, moderation/operator cover, supported native builds and the documented security/device acceptance work.
