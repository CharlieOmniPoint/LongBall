# Verified offline match downloads

DS10 is implemented by the maintained runtime contract alongside the unchanged supplied contracts. The runtime representation keeps the existing `MatchState` projection and event envelope: event wire schema1, `longball.events/1.1`, current capture engine4. The independent snapshot schema is1 and its checksum serialization is `longball.canonical-json/1`. Historical accepted envelopes retain their original schema/engine labels; they are not relabelled as current capture events.

`GET /v1/matches/{matchId}/download?deviceId=…` is the current assigned adult manager's accepted checkpoint view. Recorder metadata is observation only. It neither acquires authority nor exposes a controller token. `GET /v1/matches/{matchId}/offline-bundle?deviceId=…` additionally requires the current unfrozen controller's exact device and `X-Controller-Token`. The capability stays in the separately retained encrypted native grant. The bundle's controller tuple binds that authority without returning a secret. The client uses this strict endpoint after acquisition. If that capability is refused, it explicitly disables recording, retains original local evidence, and may refresh an assigned-manager snapshot for viewing only. An observation can never reconfirm the refused capability.

Both SQLite and PostgreSQL assemble the response inside the existing domain transaction lock. Match projection, current grant, requested-device checkpoint, accepted event rows, actual controller transitions and recorded publication classification are read within that transaction. A concurrent application write waits until the snapshot is complete. The accepted history contains every persisted accepted envelope in revision order, with its original server receive time; quarantined events stay in the separate recovery/outbox paths. Up to10000 accepted records are supported, matching the supplied pilot bound. Control transitions preserve their own original IDs/epochs in a separate array, also bounded to10000, because the existing runtime never allocated them global match-event sequence numbers. Neither stream is truncated. Missing/inconsistent or unsupported history returns422. No tighter payload-byte limit is introduced by this change.

`state.config` retains the immutable fixture, rules, selected players, match-time profile preferences and formation slots. `state.lineup`, `state.stagedLineup` and the complete accepted domain projection travel with the same checkpoint. `publication` includes only the actually recorded fixture class, classification version, result publication policy and sharing policy. Unknown classification/version/policy stays null; unapproved sharing remains unapproved. The original fictional seed’s player `available` boolean remains legacy selection metadata and never substitutes for recorded attendance. No account contacts, birth dates, private ballots or galleries are included. The observed server time and original clock evidence do not establish a continuous device clock or let a new phone inherit another phone's monotonic origin.

The checksum covers every response field except `checksumSha256`. Objects use ascending UTF-16 code-unit key order, arrays keep their order, and primitive escaping/number representation follows `JSON.stringify` (including negative zero becoming zero). There is no Unicode normalization or locale collation. Values must be finite plain JSON with dense arrays; cycles, undefined values, accessors and hidden/symbolic fields are refused. The resulting text is encoded as UTF-8 without a BOM and hashed with SHA-256, returned as64 lowercase hexadecimal characters. Noble2.4.0 supplies the maintained hash implementation. Incremental hashing uses bounded temporary encoding chunks; it requires neither host `crypto` nor `TextEncoder`. This checksum detects payload corruption and inconsistent installs over authenticated transport; it is not a separate server signature or policy approval.

Before journal replacement, the client checks the checksum, snapshot/wire/engine versions, bound match/device/team/season, projection revision, complete ordered accepted history, command identity, checkpoint, recorder metadata and clock observation. Original accepted command metadata is compared with the actor-bound projection without rewriting the retained envelope. Original historical engine labels remain evidence. Controller capabilities and private profile extras are rejected in the snapshot metadata.

The installed document stores the accepted projection once, plus the complete checksummed metadata/history. Journal reload revalidates that payload. Installation uses the existing atomic journal transaction/CAS; a corrupt/incomplete response cannot replace the last usable document. Pending/quarantined events, original uncertain request bytes and local candidate branches remain retained through successful refreshes too. Existing unsigned caches remain readable for recovery, but recording requires a fresh verified snapshot. There is no automatic erasure, event relabelling, authority acquisition, policy acceptance or reconciliation of an old stream.

Focused evidence is recorded in `evidence/2026-10-21/offline-bundle.json`. The upper-bound fixture checks10000 accepted-record shapes with long permitted reason strings; it is not a played-match or physical-device performance claim. Actual SQLite/restricted PostgreSQL HTTP checks verify persisted original envelopes, receive metadata, capability refusal and transaction consistency. Native storage, restart, prolonged offline clock continuity and device performance still require physical-device acceptance. Production browser private caching remains disabled; fictional browser journals remain explicitly fictional.
