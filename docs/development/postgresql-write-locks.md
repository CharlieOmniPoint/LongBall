# PostgreSQL write coordination

Match mutations may run concurrently for independent teams. A transaction qualifies only when its immutable, resolved actor context has operation `match.manage`, requested role `manager` or `default`, and canonical club, team, season and match IDs. HTTP input does not supply this context: the request boundary resolves match ancestry before opening the transaction, and current membership and database row policies still apply inside it.

Eligible transactions acquire the existing `longball:domain-write:v1` bigint advisory lock in shared mode, then acquire an exclusive two-integer advisory lock derived from the namespace `longball:team-write:v1` and the resolved club/team pair. The team key intentionally spans seasons and matches. Hash collisions conservatively serialize additional teams. PostgreSQL separates the two-integer advisory namespace from the bigint namespace.

Every other explicit write transaction retains the existing exclusive global advisory lock. This includes account, permission and preparation changes, workers, migrations, incomplete contexts and lower roles. A global writer waits for all active match transactions; new match transactions wait behind a queued global writer. Older application instances using the original exclusive global lock therefore remain compatible. This does not replace row security or current authorization checks.

Nested transactions reuse the already-held lock and require the exact same application context. They cannot change operation or scope, nor upgrade an implicit unlocked read transaction to an explicit write. Commit and rollback release both transaction-scoped advisory locks. The connection-pool limit, database timeouts, command limits and idempotency boundaries are unchanged.

Device IDs remain globally unique. After an insert that can encounter a concurrent conflict, device binding verifies that the committed row belongs to the current account before granting match control. A competing account receives `409 DEVICE_ACCOUNT_CONFLICT`; the command and its receipt roll back. The same account may reuse its device ID in another authorized team.

`postgres-write-locks.test.ts` exercises independent connections with actual PostgreSQL advisory waits: independent-team progress, same-team serialization across seasons, legacy global interlock in both directions, rollback and nesting, conservative handling of other contexts, and fresh membership revocation after waiting. `postgres-device-race.test.ts` uses two real API instances and an insert barrier to check the global device race, hidden existing ownership and same-owner reuse. These checks establish coordination and authorization properties; the separate quiet performance benchmark determines whether QL04's latency target is met.
