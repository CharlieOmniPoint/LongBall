# PostgreSQL scope and runtime security

SEC10 is implemented through central migrations005–012, media feature3 and activation feature2. Separate migration credentials own the schema; serving API and worker roles are non-owner, non-superuser and NOBYPASSRLS. Startup rejects privileged role membership, schema/table ownership, wrong API/worker login purpose, missing migrations or missing RLS installation. Production startup uses verify-only mode; the runtime cannot seed clubs or create its own authority.

The migrator-owned `runtime_roles` map binds `session_user` to API or worker purpose. Definer functions use a fixed `pg_catalog,longball` search path and explicit EXECUTE grants. API identity/actor/activation contexts cannot grant a worker login user access, and an API login cannot adopt even a valid worker lease. The schema owner is a separate operator boundary; its fixture/migration privileges are never issued to a serving process. Worker claims and job contexts require worker purpose even for operator fixtures.

`PgDatabase.withContext` holds logical asynchronous request context, not a long SQL transaction. Every standalone query opens a short transaction, installs parameterized transaction-local JSON with `set_config(...,true)`, then commits or rolls back and releases its client. Mutations pin one connection and retain the existing advisory transaction lock. Context changes must wrap the SQL transaction before BEGIN; changes inside an open transaction are rejected. Nested logical scopes retain the verified identity, selected role and existing scope. Ended ancestors and released transaction frames reject delayed work. Pool reuse, concurrent requests and rollback cleanup are covered by actual PostgreSQL tests.

JWT verification precedes identity lookup. Identity discovery can see only its issuer/subject account, then actor policies validate that account and current unexpired/unrevoked memberships. Selected administrator context cannot read ordinary match/preparation/community/report endpoints. Internal staff, configuration and season operations use explicit operation/kind allowlists. Global account privacy requests use own-account scope; scoped leave requests carry their actual team and season. No request fulfils erasure or changes memberships by itself.

Recorded clubs, teams, seasons and game contexts provide relational ancestry. Match-event children and media manifests use composite foreign keys; insert triggers derive scope from authorized parents and reject contradictory scope. `game_contexts` records both accepted native games and existing scoped community game records without fabricating an event stream or MatchState. Legacy club ancestry is backfilled only from recorded preparation data. Ambiguity aborts migration; missing ancestry is retained as unresolved and denied to runtime roles.

Thirty-four account/tenant tables have RLS in the current source. Aggregate JSON documents still need the existing safe DTO projections for field-level privacy, own ballots and reports; RLS does not replace them. Media policies additionally require current publication, exact reviewed revision, current sharing and hidden-uploader rules before another player/spectator can read its manifest. The private gateway independently repeats application authorization and serves no-store bytes.

The worker obtains a bounded due job through `claim_due_job`, which stores a hash of its random lease capability. Subsequent queries require that exact job, immutable stored club/team/season, capability and live lease. Database time alone determines due/reclaim eligibility and the 30-second lease interval; worker observations outside 30 seconds of that independent clock are rejected. Job validation also requires stored due time to have arrived and the lease to lie within the database’s current 30-second bound, so a future capability created before migration009 cannot authorize early work after upgrade. Original ledger rows remain preserved. Database time bounds expiry even if logical context is stale. Notification evidence is limited to its actual recipient; award changes are limited to the claimed game. `enqueue_award_notification` accepts only an allowlisted generic initial payload for that claimed award and current recipient. An immutable source-job foreign key and unique source-job/recipient ledger prevent additional business keys from multiplying fanout. The worker cannot read account privacy requests or media manifests. The shared accounts policies also resolve spectator capability predicates for worker queries; EXECUTE is granted on those predicates, but their login-purpose checks return false for a worker and no invitation-table access is granted. No push provider delivery is claimed.

Anonymous activation requires the hash of the original opaque token, including at completion. The final account enablement context is installed only after independent provider verification and exact provider assertions. Token-only redemption cannot enable an account or change its provider identity. Wrong/missing original capabilities fail without provider completion authority.

Migration010 gives uploaded club/team logos separate seasonless ancestry and a composite foreign key from each current slot to its exact asset revision. Club-logo writes require the selected administrator role; team-logo writes require the selected assigned manager role. A selected administrator does not inherit manager powers. Slot updates advance a compare-and-set revision; only current pointers are readable by other current members, while replaced or removed uploads remain private. The API scanner/decoder adapter is the trusted writer of processing evidence, as with game photos; SQL does not independently verify antivirus verdicts. Published bytes/evidence and ancestry are immutable, while an owner's retried preparation may rotate its opaque transport token. The administrator branding-name helper returns only scoped club/team names and age group, never a raw preparation document.

Migration011 stores only domain-separated SHA-256 invitation verifiers. Its atomic retirement removes legacy plaintext from invitation records, command fingerprints and retained responses, preserves accepted grants/history, and requires explicit reissue for pending old credentials. Legacy rows carry no approved policy version and cannot preflight. Current players can issue or reissue their own pending invitations; managers remain scoped to their current team and season. Existing-account destination inspection requires verified account context and the exact possessed-token hash; it returns only trusted destination metadata and creates no membership. First-spectator activation reserves at most one disabled, unclassified account per invitation and one current provider attempt. Only independent provider verification followed by the exact retained token/attempt context can activate it. The reservation itself grants no membership or adult authority.

Native app enrollment metadata lives in `native_app_devices`, separately from match-controller identities. Its policies require the current verified account and issuer without a team-membership prerequisite. PostgreSQL stamps registration and monotonic last-seen times; platform remains client-reported. Enrollment cannot adopt another account's identifier and grants no match-controller capability. The schema9 container/paired-restore evidence remains a historical checkpoint; schema11/12 source tests and subsequent runtime rehearsal are recorded separately. Migration012 adds canonical still HEIC to photo/logo MIME constraints without widening row policies. The maintained native codec runs only after the private original scanner verdict; the final community/photo link requires exactly one manifest update inside the same transaction, so a changed authority rolls back the community revision.
