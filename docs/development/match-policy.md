# EV05 prospective match policy

`policy.changed` uses the ordinary durable controller command, ordered canonical outbox, authenticated upload and accepted download. The API assigns its actor. The command records the source match revision, preceding/new policy versions, schema version, captured effective boundary and manager reason. Its payload has the supplied canonical PolicyPayload fields; the runtime additionally records explicit applicability and soft half-buffer preferences.

Minimum stint and batch values remain **soft preferences**. Confirming them never creates a mandatory five-minute rule, batch cap, substitution grid or automatic player movement. Score threshold and return-to-normal are explicit. Q07 remains `unapproved`; a keeper-policy transition is refused because this service has no separately authorised experimental transition gate. It is not approved by a client field, role selector or saved template.

The reducer closes active time under the prior policy, applies the new settings at the captured continuous boundary, then accrues only any still-uncommitted suffix under the new policy. Committed earlier participation, targets, goals, config and events remain unchanged. Paused/half-time changes add no active time. Backdated committed boundaries, invented future play, uncertain clock evidence, stale sources/versions and terminal-match changes are refused. Policy boundaries and versions are retained when an independently authorised participation correction rebuilds target intervals.

Accepted state carries immutable policy history and the derived sticky score-position mode. A deliberate manual reset is another policy version with a reason; it does not alter the original lineup or a previous event. Policy correction/void semantics that would reinterpret historical targets remain outside this prospective command and require the separately governed history-review path.

Reusable preparation may attach `initialPolicyProposal` and `initialLineupProposal`. These are validated review drafts only. Creating/downloading a match neither confirms the policy, stages players, infers attendance nor grants authority. A new controller policy event and normal lineup validation/confirmation are still required.

The engine identifier is `synthetic-live-4`. A client that only understands v3 must fail closed on the new policy-bearing projection rather than silently ignoring settings. The archived v3 fixture was generated with the unmodified f4fbffe v3 engine before implementation and includes retrospective participation review. Focused replay checks reproduce both v2 and v3 accepted projections exactly without inserting policy defaults. Existing old-version wire envelopes and event identities are never relabelled; the service retains/version-quarantines them and preserves their reserved stream sequence.

Core evidence: nine policy tests, two archived replay tests, ten participation-correction tests and an actual SQLite HTTP test covering accepted policy, deliberately lost response/exact retry, two handovers, persistent per-device sequence, old-version retention and child role-escalation denial. Native storage, touch, force-stop and actual handover clock continuity remain separate device tests. UI integration and the runtime schema are completed in the follow-on integration change.
